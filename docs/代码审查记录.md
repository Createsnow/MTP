## 3. 核对过、确认没有问题的点（不改代码）

| 位置 | 核对内容 | 结论 |
| --- | --- | --- |
| 全部路由 | 每个接口声明的角色依赖与 PRD F-02 的角色表是否一致 | 一致：写操作都是 `OperatorDep` 以上，配置类为 `AdminDep`，账户管理为 `SuperAdminDep`，痕迹为 `AuditDep`；读接口在服务层按授权范围过滤（`scope_sql`、`check_read`） |

| `db/mysql.py` `_begin` | 提交失败、回滚失败时连接是否会带着坏状态回到池里 | 断线类错误（CR 2000–2999）与回滚失败都标记丢弃；服务端错误（死锁、锁等待超时）回滚后连接照常可用，放回池中；`after_tx` 在提交和回滚后都执行，跟事务走的前缀锁不会泄漏 |
| `services/locks.py` | 多把命名锁加锁顺序、部分拿到时是否释放 | 按键排序依次加锁；任一把拿不到即全部释放、关闭独立连接 |
| `generate.generate / _run` | PI 操作锁在当场生成、后台生成、出错各路径是否都释放；死锁重做是否会重复写 | 三条路径都在 `finally` 释放；死锁时整笔已回滚，`retry_deadlock` 只在没有外层事务时重做；进度写在独立事务里，可重复 |
| `generate.recover_interrupted` | 是否会把仍在执行的任务误标失败 | 生成全程持有 PI 操作锁，拿得到锁才回收，并用 `NOWAIT` 再确认计数行未被占用 |
| `delivery.push._claim_task` | 多实例认领是否会超出组织推送并发 | 互斥行 `#push_claim` 加锁读放在事务第一句，之后的计数读到别的实例已提交的认领；认领用 `state + updated_at` 条件更新 |
| `users.mes_authenticate` | 失败计数、锁定、解锁；缓存的密钥摘要在重置密钥、停用后是否失效 | 计数与锁定在行锁内；缓存按口令版本（重置即变）比对；停用、IP 白名单每次都读库判断 |

## 4. 观察到、本次不改的点

以下不是缺陷或改动收益不足以抵消风险（已联调通过的行为不动），记录备查：

| 位置 | 现象 | 不改的原因 |
| --- | --- | --- |
| `generate._run` | 当场生成（不超过 `SN_GEN_SYNC_THRESHOLD`）被别的页面取消时，各单据各记一条失败痕迹，接口再由全局异常处理记一条 `POST /api/generate/run` 的失败痕迹 | 代码注释明确取消要按单据留痕；多一条请求级痕迹不影响业务，改了会改变审计条数 |
| `generate` 后台线程池 | `executor` 固定 4 个线程，`SN_GEN_CONCURRENCY` 调到 4 以上时后台任务最多 4 个并发（当场生成不受影响） | 默认值就是 4；调大只是后台任务多排一会儿队，不会出错 |
| `transfers.transfer_bill / direct` | PI 操作锁按锁外第一次计算的目标 PI 加，锁内重新计算时目标单据的 PI 若恰被同步改了，锁的是旧 PI | 号按来源 PI 选取并 `FOR UPDATE`，来源 PI 照常互斥；目标 PI 上的生成不读这些号，只是同一瞬间同步改 PI 的极小窗口，不改 |
| `changes._on_present` 失去对应 | 只按物料行计数（`sn_line_count`）判断；只有 SN 导入的号的物料行（导入不计计数）被删或换物料时不提醒、不暂停 | 导入功能按设计不进物料行计数；是否对导入号也做失去对应提醒属业务口径，需业务方确认后再定（见 PRD F-06） |
| `deletion.delete` 额度 | 删掉转入的号时额度还给号现在挂的物料行（本单生成数减去删掉的枚数），而这一行转入时并没有计入这些号的本单生成数。例：目标行订单 10 枚已全部生成，转入 5 枚后删掉这 5 枚，目标行可再生成 5 枚，这一行累计生成 15 枚，超过订单数量；生成它们的原行额度不回来 | PRD 文首 2026-11-02 变更第 3 条、业务说明明确「额度还给号现在挂的物料行，生成它的那一行不变」，按现行规则实现；是否改为「还给生成它的物料行」须业务方确认 |
| `k3.fetch_approved_heads` | 比对同步取表头时金蝶按明细返回多行，排序只按单据编号（`FBillNo ASC`），分页边界落在同一单据的几行之间时，个别行可能重复或漏掉；明细查询已按「单据编号 + 分录内码」稳定翻页 | 漏掉整张单据时：已出号单据同一周期按单号复查、写回快照；未出号单据下个周期（10 分钟）回来，影响有限。改排序会改变调金蝶的请求（每页行数、性能），测试环境的假金蝶不分页、验证不了，建议与金蝶实施方确认后再改为 `ORDER_BY` |
| `query.read_scope` 同 PI 各组织只读 | 普通操作员切到「同一 PI 各组织」时只校验本组织在这张 PI 下有号；再按流水范围查时按流水归属 PI 查，转到别的 PI 的号（流水仍属这张 PI）也会列出（只读） | 属于同一 PI 流水的号，按 Q2 的口径可以接受；是否只限当前 PI 须业务方确认 |
| `sn_import` 留痕起止号 | 导入、整单删除的留痕起止号按字符排序 | 导入的号是现场已有的号，没有流水与位数规则，按字符排序即可；与 FIX-10 的生成号不同 |

## 17. 订单页、生成页列表加载慢（2026-11-16）

背景：测试环境反映订单页、生成页加载慢，问「是不是全部数据都展示」。排查结论：

- **订单页左表**已是服务端分页（每页 20 张单据），只传一页数据；但每翻一页都要把整张快照（`sn_prd_mo` 连 `sn_line_count`）按单据汇总、排序后才取 20 行，耗时随快照总量增长，与页码无关。
- **生成页 PI 列表**原来不分页：接口一次返回最多 500 张 PI（`workbench.LIST_LIMIT`），页面不搜索时只显示最近 3 页（60 张），搜索时显示全部匹配；接口对这 500 张 PI 都统计号池（`item_stats`、`gen_own`），对前 60 行逐张判断「需先选规则 / 不能生成」时**每张 PI、每张单据、每个物料行都单独查库**（单据冻结 / 失去对应每张单据 2 条，PI 没绑规则时每个物料行重查一次 PI 绑定），一次请求上千条 SQL。
- **普通操作员（带授权范围）更慢**：对 500 张 PI 统计号池时，授权范围条件（`item_scope_sql` 的 OR 子查询）加上 IN 列表超过 200 个值，MySQL 估错行数，改为**全表扫描号池** `sn_item`，号池越大越慢。

确认的要求：**MES 联调接口（`/api/mes/v1` 与推送报文）不变**；页面接口可以改（生成页 PI 列表加分页参数）；**每个列表由一条 SQL 独立取出**，不先用一条 SQL 取出一部分（如本页单据编号）再用另一条 SQL 补全。

本机压测（MySQL 8.0；6 万张单据 / 18 万物料行 / 2 万张 PI，号池 150 万个号；原始代码与改后代码对同一份数据各请求一次）：

| --- | --- | --- |
| `GET /api/orders`（第 1 页，系统管理员） | 705 ms | 126 ms |
| `GET /api/orders`（第 3000 页） | 734 ms | 168 ms |
| `GET /api/orders`（第 1 页，普通操作员） | 496 ms | 154 ms |
| 生成页 PI 列表「待生成」第 1 页（系统管理员） | 1928 ms，1769 条 SQL，167 KB | 约 300 ms，41 条 SQL，7.5 KB |
| 生成页 PI 列表「待生成」第 1 页（普通操作员） | 2237 ms，1388 条 SQL | 约 0.5 s（号池统计不再全表扫描） |
